Team-managed ↔ company-managed, which nothing else does

If you have tried to clone between the two, you have met this:

"This app does not work for this use case. It will only work from Team → Team or Company → Company."

They are not being lazy. A team-managed project's custom fields and issue types belong to that project: "Acceptance criteria" is customfield_10234 on one side and customfield_10891 on the other, and they share no identifier at all. Send the source's field ids to the other project and Jira rejects every one of them.

Ditto stops treating a field id as the field's identity. It matches fields on name and type, against the target project's own create screen, and re-resolves dropdown, version, component and priority values by name too — because an option id is just as project-scoped as a field id. Issue types are matched by name, then by spelling (“Sub-task” and “Subtask” are the same type to everyone except a string comparison), then by hierarchy level.

Where it cannot place something, it says so — by name, before you run it.

What you get

Deep clone one work item. From the ⋯ menu on any work item: it, its sub-tasks, an epic's children, as deep as you ask. The hierarchy is rebuilt against the copies — a copied sub-task hangs off the copied parent, not the original.

Bulk clone a search. From the work item navigator: tick some rows and clone those, or clone everything your JQL matched. Up to 2,000 work items in a job.

Attachments, actually copied. Streamed from the original to the copy inside Atlassian's network. Anything over the per-file limit is named, sized and reported — never silently missing.

Links kept straight. Links between two work items in the same job are re-pointed at the copies, so you get an independent tree rather than two tangled ones. Links to work items outside the job keep pointing at the originals. Each link is created once, not once per end. Web links come across too, and every copy can be linked back to the work item it came from.

Rename as you copy. CLONE: {{summary}}, {{key}} — {{summary}}, or anything else.

Field overrides. Set a value on every copy — a fix version, a label, a component — at clone time.

Sprint placement, best-effort. A sprint id means nothing on another board, so Ditto matches by name, prefers an open sprint, and will not put work into a finished one. See the limits below: this one is not always available, and the app tells you when it is not.

A job log that explains itself. Every clone is a job you can open: how far it got, what it created, every field with no home in the target, every attachment over the limit, and every value the target project refused. Find everything one job made with dittoJob = "<id>" in JQL.

No setup. None. There is no project settings page, no per-project enablement, nothing for an admin to repeat for every project. Ditto is available everywhere the moment it is installed.

Built for real Jira sites, not demos

  • A rate limit is a pause, not a lost job. Jira Cloud's API budget is shared across every site using an app. Ditto estimates a job before it runs, takes at most a quarter of the hourly budget per pass, backs off when Jira asks, and checkpoints, so a paused job carries on by itself from where it stopped.
  • Running twice never makes two copies. Every work item Ditto creates carries a marker keyed to the job and the original, so a retried or re-delivered job is a no-op — and an interrupted one adopts what it already made instead of duplicating it.
  • One awkward value does not lose the tree. If the target project refuses a field — an assignee who is not assignable there is the usual one — Ditto drops that field, retries, and records what it left empty, rather than failing the work item and everything under it.

Runs on Atlassian

Ditto declares no external permissions at all: no fetch, no egress, no remote backend, no third-party service. Your work items, attachments and job records never leave Atlassian's infrastructure. Attachments are moved Jira-to-Jira and are never stored by us.

What Ditto does not do

We would rather you read this here than find out afterwards.

  • It does not copy a project. There is no copy-project API on Jira Cloud (JRACLOUD-83539) — not for us and not for anyone. Ditto clones work items, in bulk and across project types. It does not copy schemes, workflows, screens, permissions, board configuration or automation rules.
  • Status, resolution and history are not copied. Copies start at the beginning of the target project's workflow. Jira does not let an app set a status at creation, and a copy that claimed to be "Done" would be worse than one that did not try.
  • Sprint placement is not available on every site. The Jira Software board API is not reliably reachable by Forge apps; where it is refused, your clone still runs, the copies land in the backlog, and the job says so explicitly.
  • Attachments have a per-file limit (10 MB by default, and a whole-job budget). Files over it are listed, with their sizes, in the preview and the job log.
  • Comments and watchers are off by default. Jira gives an app no way to attribute a copied comment to its original author, so copied comments would appear under the name of whoever ran the clone. It is offered; it is not on unless you ask.
  • 2,000 work items per job. A larger selection is refused with the number in the message, rather than half-copied.
