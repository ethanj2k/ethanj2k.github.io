The number is in Jira, not just on the screen

This is the part most calculated-field apps on Cloud get wrong, and it is not their fault: Forge invokes a custom field's value function only on the issue view. An app built that way shows you the right number on the work item and a stale one — or nothing at all — on the board, in the backlog, in a JQL search and in a CSV export.

Slide Rule does not compute on read. It recomputes when something changes and writes the value into Jira's own index, so:

  • board cards show it, because it is a field value like any other;
  • "Total story points" >= 100 is an ordinary JQL clause;
  • CSV and Excel exports carry it, without a plugin or a workaround;
  • dashboards, filters and Automation rules read it the way they read Story Points.

Nothing in Jira has to know this app exists for the number to be there.

A formula language that is actually a language

The loudest complaint in this category is aimed at the market leader, by its own customers:

"Has EXTREMELY limited scripting capabilities in Jira Cloud."

So the language is the product:

{Story Points} + SUM(CHILDREN({Story Points}))
IF({Time Spent} > {Original estimate}, "over", "on track")
WORKDAYS_BETWEEN(NOW(), {Due date})
SUM(LINKED({Story Points}, "is blocked by"))
ROUND(100 * COUNT(CHILDREN({Resolution})) / COUNT(CHILDREN({Summary})), 1)

Real precedence. Short-circuiting and / or, so {Divisor} != 0 and 10 / {Divisor} > 1 is safe to write. IF, COALESCE, ISBLANK, IFERROR. Rollups over children, the parent and links — narrowed to one link type when you want it. SUM, AVG, MIN, MAX, COUNT. ROUND, FLOOR, CEIL, ABS. CONCAT, UPPER, LOWER, TRIM, LEN, LEFT, RIGHT, CONTAINS, REPLACE. NOW, TODAY, DAYS_BETWEEN, WORKDAYS_BETWEEN, DATE_ADD, and date arithmetic that knows the difference between a calendar day and Jira's eight-hour working one.

Field names go in braces, exactly as Jira spells them: {Story Points}, {Due date}.

When a number is wrong, the work item tells you why

Every work item carries a Slide Rule panel showing the formula, the values it actually read on this work item, what it produced, and when. The support question in this category is always "why does it say that", and the answer is on the screen instead of in a ticket.

It refuses rather than guessing

A wrong number that looks reasonable is worse than a blank one, so Slide Rule writes nothing — and says so on the work item — when:

  • the work item has more than 1,000 children, or more than 50 links, so the rollup could only ever be partial;
  • a contributing work item carries an issue-level security level, or a child sits in a different project from its parent. The value is readable by anyone who can open the work item it lands on, and we will not turn a restricted child into an aggregate that everybody can read;
  • the formula returns something the field cannot hold — text into a number field is refused, not silently written as zero.

It also treats an unknown field name as an error, not as blank. A typo that reads as zero is how a wrong total reaches a board and nobody notices for a month.

No per-project setup

There is no per-project configuration screen, because there is nothing to configure per project. A field defined with no scope applies to every project and every work item type the moment you save it, and scoping it to certain projects is one field on the same form.

The one Jira step that remains is the one every custom field needs: add the field to a screen if you want it visible on the work item itself. Board cards, JQL, filters and exports do not need it — the value is in Jira's index either way — and the Slide Rule panel on each work item shows the value and the formula whether the field is on a screen or not.

Runs on Atlassian

The manifest declares no external permissions of any kind — no fetch, no egress, no remote backend, no analytics, no runtime AI call. The app is not technically capable of contacting any host other than Atlassian's own APIs, and every value is computed inside your own site. Two of the five apps in this category cannot say that.

What it does not do, said before you buy

  • Convergence is quick, not instant. A value is recomputed on an event, so it lands moments after the change, not in the same keystroke.
  • A rollup stops at 1,000 children and 50 links, and refuses past that rather than publishing a partial sum.
  • Calculated fields are read-only, deliberately: the app owns the value, and a typed-over one would be overwritten on the next recompute.
  • No cascading-select or dynamic create-screen behaviour. Atlassian's jira:uiModifications explicitly does not support Forge custom fields, so an app that sells both is selling two features that cannot meet. This one calculates.
  • Not Cloud Fortified. That is a Marketplace programme a vendor applies to once an app has install volume and a support history. The technical bar underneath it — Runs on Atlassian — is met from day one.
