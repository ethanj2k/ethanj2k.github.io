Git Links for Jira — every commit, branch and pull request on the issue, on five hosts, for a fraction of the price

Tagline: Commits, branches, pull requests, builds and file browsing from GitHub, GitHub Enterprise, GitLab, Bitbucket and Azure DevOps — on the issue, searchable in JQL, with smart commits your project admin turns on. Free for 10 users, then US$0.90 per user per month.

Summary

Git Links for Jira puts the code behind a piece of work where the work is. Connect a repository once and every commit, branch and pull request that mentions the issue key shows up on the issue, with the files changed, the diff, the build status and how far the branch is ahead of main. Create a branch and open a pull request without leaving Jira. Browse any connected repository, at any branch, from a Git Viewer page inside Jira. Search all of it with JQL.

Five hosts, one app: GitHub, GitHub Enterprise Server, GitLab (SaaS and self-managed), Bitbucket Cloud and Azure DevOps (Services and Server). Webhooks index a push the second it lands; an hourly sync catches anything a webhook missed.

Highlights

  • The issue panel, in full. Commits with author, time, message and files changed; branches with ahead/behind against the default branch; pull requests with open / draft / merged / declined; CI builds and deployments per branch; inline diffs rendered in Jira; a one-click git switch command; and manual linking for the commit whose message forgot the key.
  • Create a branch, open a pull request. Both from the issue, both through the provider's API. Branch names come from a template you control ({prefix}{key}-{summary}, plus {type} and {user}), are always valid per git check-ref-format, and never collide with an existing branch.
  • Git Viewer. Browse the file tree of any connected repository at any branch and read files inside Jira, with syntax highlighting. No context switch to answer "what does that file look like on the release branch?".
  • Smart commits that are opt-in, per project, by an administrator. #comment, #time, #transition and #label are always parsed and shown on the issue. They are only ever executed if a Jira or project administrator turns execution on for that project and allow-lists each command family. Every write carries an audit line naming the commit, the repository and the author the commit claims. Replays and retries cannot double-apply anything.
  • Repository permissions. Every repository is scoped to the Jira projects that may see it — enforced on reads and on the way in, so a repository scoped to one project cannot index, comment on, or transition anything in another. "Every project" is a deliberate tick, not what happens if you leave the picker alone.
  • JQL, dashboards and filters. Each issue's git activity is written to an indexed issue property with twelve search fields: gitCommits, gitBranches, gitPullRequests, gitOpenPullRequests, gitMergedPullRequests, gitDeclinedPullRequests, gitHasCommits, gitHasPullRequests, gitMerged, gitLastActivity, gitRepository, gitBranch. Example: project = PLAT AND status = Done AND gitHasCommits = "no" finds work marked done with no code behind it.
  • A project page worth opening. Recent commits, branches and pull requests across the project, per-contributor activity, and an "attention needed" list of pull requests that have been open too long.
  • Credentials the way your organisation works. One site token, a token per user (so the provider's audit trail names the right person), or no token at all for a public repository. Administrators can require personal tokens for anyone creating branches or pull requests, and can delegate app administration to a group without handing out Jira admin.
  • Instant and reliable. Per-connection webhooks with HMAC-SHA256 (GitHub, GitHub Enterprise, Bitbucket), shared-token (GitLab) or HTTP Basic (Azure DevOps) verification, compared in constant time, with replay protection. Plus an hourly sync that works to a deadline and picks up next hour exactly where it stopped, so a repository with thousands of branches still gets indexed.

What is not possible on Forge, and why

Two things the incumbent does that a Forge app cannot, stated plainly rather than promised:

  1. Populating Jira's built-in Development panel and its development[...] JQL. Those are fed by the Jira Development Information API, which is available to Atlassian Connect apps that declare a jiraDevelopmentTool module. Forge has no equivalent module and cannot request those scopes. We ship the same capability as a first-class issue property with twelve JQL fields instead; the data lives on the issue, is readable by Automation and the REST API, and travels with the issue.
  2. Connecting to a git server over SSH, or to a host with a private or self-signed TLS certificate. Forge egress is HTTPS-only to declared domains, with a fixed trust store and no raw sockets or filesystem, so there is no way to speak the git protocol or clone a repository. Every supported host is reached through its HTTPS REST API. This also rules out Gerrit-over-SSH and generic self-hosted git servers with no REST API; AWS CodeCommit is closed to new customers by AWS and is not a live gap.

One smaller, honest note: gitRepository and gitBranch match a whole repository or branch name, not a fragment of one — gitBranch ~ "release/2.0", not gitBranch ~ "release". That is how Jira indexes a text entity property.

Security and data handling

  • Not "Runs on Atlassian". The app calls your git host's REST API from the Forge backend, which is inherent to the product — the incumbent is not "Runs on Atlassian" either. Nothing else leaves Atlassian. All indexed data lives in Forge storage in your installation, and the JQL summary lives on the issue itself.
  • Scopes: read:jira-work, write:jira-work, read:jira-user, storage:app. write:jira-work exists solely for smart-commit execution. Forge cannot request a scope conditionally, so it is always declared and every write is gated server-side on the per-project toggle, which defaults to off. With it off the app writes nothing to an issue except its own JQL summary property.
  • Egress: api.github.com, gitlab.com, api.bitbucket.org and dev.azure.com are declared explicitly. A wildcard remains for the three features whose hostname is unknowable at manifest time — GitHub Enterprise Server, self-managed GitLab and Azure DevOps Server, plus the optional alert webhook — because Forge has no runtime domain registration. It is narrowed at runtime to a public DNS name whose last label is an alphabetic TLD (which rejects every inet_aton spelling of an IP literal, including 0x7f.1), never localhost or an internal suffix, https only, port 443 only, no embedded credentials, and redirects are never followed so a 30x cannot carry your token anywhere.
  • Tokens are held only in Forge secret storage. They are never returned to a browser, never written to a log, never placed in a URL and never included in an error message.
  • Webhooks are verified before the body is parsed, in constant time, against a per-connection secret, with replay protection by delivery id. A missing secret and a wrong signature are indistinguishable from the outside: both are 401.
  • Smart-commit authorship. Writes are made by the app, not by the commit author — a git author is self-asserted (git commit --author=…), and the app never treats it as proof of identity. The audit line says so explicitly.
