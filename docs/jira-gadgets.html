Tagline: Sprint burndown, velocity, cumulative flow, cycle time, release burndown, epic progress, WIP and a pivot table — as native Jira dashboard gadgets that run entirely on Atlassian. Free for 10 users, then US$0.60 per user per month.

Summary

Agile Gadgets adds eight dashboard gadgets to Jira. Point each one at a board, a project or any JQL query, and it draws the chart a delivery team actually argues over in a stand-up: what is left in the sprint, how much the team really finishes, where work piles up, how long things take, and whether the release date is credible.

Every chart is rebuilt from Jira's own issue history rather than from a snapshot, so a burndown knows what the scope was on the day, a velocity chart knows what was committed at the sprint's start instant, and a cumulative flow diagram knows which column each issue sat in three weeks ago. Days are bucketed in the viewer's own Jira timezone using calendar arithmetic, so a chart does not shift by a day for a colleague in another country or across a daylight-saving boundary.

Everything runs on Atlassian infrastructure. There is no vendor server, no data export, and no egress: the app reads Jira as the person looking at the dashboard, so a gadget can never show anyone an issue they could not already open.

The gadgets

  • Sprint burndown / burnup — remaining work falling to zero, or completed work rising to meet scope, in story points or issue count. Ideal line on calendar or working days. Scope changes are marked with the issue keys that were added, removed or re-estimated, and the baseline is taken at the sprint's start instant, so planning-day additions count as commitment rather than churn.
  • Velocity — committed versus completed for the last N closed sprints (1–24), with scope added and removed in between, per-sprint attainment, and running averages. Committed is measured at the sprint's start instant and completed at its completion instant, so committed + added − removed always reconciles.
  • Cumulative flow diagram — how much work sat in each workflow status at the end of each day, for a window of 2–365 days, replayed from status history. Bands never go negative and always sum to the day's total; work in a status no column claims is reported rather than dropped.
  • Cycle time / lead time — every issue that finished in the window, as a run chart against P50/P85 reference lines and a 10-issue rolling mean, or as a histogram. Percentiles are nearest-rank, so "85% of items finish within P85 days" is literally true of the listed issues. Cycle time runs from first in-progress; lead time from creation.
  • Issue statistics / pivot — count issues or sum story points by any field, in one or two dimensions, as a table, bar chart or pie chart. Row totals, column totals and the grand total always reconcile with the cells, and multi-valued fields such as labels are counted once per value with that stated in the gadget.
  • Release / version burndown — a fix version burning down (or up) towards its release date, with historical fix-version membership taken from the changelog, so issues added to the release late show as scope change rather than rewriting history.
  • Epic progress / work breakdown — done, in progress and to do per epic, computed from the epic's children. An epic's own status never inflates its own progress; orphans are grouped under "No epic".
  • WIP by status — what is in progress right now, per status, with the age of the oldest item and the average age in that status.

Every gadget offers its underlying series as CSV. UI Kit cannot write a file, so the CSV appears as copyable text in a modal; cells are hardened against spreadsheet formula injection.

Versus Great Gadgets (StonikByte)

Great Gadgets is the incumbent: 4.4★ from 49 reviews, roughly 3,700 installs, US$1.00 per user per month annually on its Standard tier at 100 users.

We match its core agile charts — sprint burndown/burnup, release burndown, velocity, CFD, cycle time trend, cycle time histogram, work breakdown, pivot table and chart — and beat it on three things: scope-change markers that name the issues, a commitment baseline taken at the sprint start instant, and "Runs on Atlassian" with no data leaving the site.

What they have that we do not, plainly: Time in Status, a per-item WIP aging chart, a WIP run chart, a team wallboard, a countdown gadget, a regional clock, a dashboard-wide controller gadget (Forge gadgets cannot yet message each other on a dashboard), free-form formula gauges, and the Advanced edition's worklog and timesheet reports. Our control chart is a run chart with percentile reference lines rather than a dot scatter, and CSV is copy-from-a-modal rather than a file download — both because a native Forge gadget has no scatter mark and no download, and we would rather keep "Runs on Atlassian" than ship an iframe. Epic-scoped burndown is not in v1; the engine is already generic over the membership rule, so it is a small follow-up.

Limits, stated up front

One gadget covers up to 1,500 issues where it has to replay issue history (burndown, velocity, flow, cycle time, WIP) and up to 3,000 where it only reads current field values (pivot, epic progress). Beyond that the gadget says so and asks you to narrow the source rather than quietly charting a subset. Boards, sprints, projects and versions are picked from lists in the gadget's own configuration form; the JQL option accepts any query you can already run.

Permissions

Read-only. The app never writes to Jira and stores nothing.

  • read:jira-work, read:jira-user — issues, changelogs, fields, statuses, projects, versions and the viewer's timezone, through the Jira platform REST API.
  • read:board-scope:jira-software, read:board-scope.admin:jira-software, read:sprint:jira-software, read:project:jira — boards and sprints, through the Jira Software agile REST API, which publishes only granular scopes. Board configuration is read for the board's saved filter and its estimation field; .admin is Atlassian's name for that read, not a write.

Runs on Atlassian

All computation happens inside Forge on Atlassian's infrastructure. The app declares no external egress, stores no issue data, and calls Jira as the viewing user so Jira's own permissions apply to every number on the chart.
